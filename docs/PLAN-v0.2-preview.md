# 批量处理「边看边存」计划

日期：2026-09-16
状态：v4。已按用户三轮反馈修订：暂存文件方案、上限降为 20 张、内存预算修正、切后台继续跑到完（前台服务）、重启即全新状态。
范围：批量模式的结果查看与保存方式 + 批量上限 + 内存加固 + 后台运行方式。单图处理（含「指定次数」和「清除当前图片」）不动。

## 1. 要解决的问题

2026-09-16 真机测试反馈：批量处理完成后，列表里**看不到处理结果**，只能先保存到相册、再点「查看」才能确认效果。用户希望在处理过程中就能看到每一张混淆／解混淆的结果，据此决定要不要保存。

根因：`BatchUi.Thumbnail` 读的是 `item.output ?: item.input`。
`item.output` 只有保存成功才有值，所以处理阶段（`READY`）永远显示 48dp 的**原图**缩略图；
「查看」按钮的显示条件也是 `status == SUCCESS && output != null`。
结果图此时其实已经在内存缓存里（`ResultCache`），只是界面没有暴露出来。

### 1.1 由此发现的更深问题（本次一并解决）

顺着"结果要能看见"这条线核对代码后发现，**用暂存文件承载处理结果**可以同时消掉三个问题，因此本次采用该方案而不是单纯的预览副本：

| 问题 | 现状 | 暂存方案的效果 |
| --- | --- | --- |
| 保存时静默重算整批 | 结果缓存只有 32 MB，装不下 20 张大图（JPEG 约 8～16 张，PNG 仅 1～3 张）。被挤出的项在保存时走 `encodeFor()` 回退，从原图**重新解码＋变换＋编码**，等于整批算两遍 | **消除**：保存直接复用暂存字节，零重算 |
| 保存路径无内存预算保护 | `encodeFor()` 会再次产生约 100 MB 峰值，且不像处理阶段那样按 `retainedBytes` 核算 | **消除**：不解码就没有该峰值 |
| 处理结果会丢 | 结果只在内存，进程被杀即失效 | **改善**：暂存在应用私有目录，切后台或进程重建后结果仍在 |


## 2. 已确认的产品决策

| 决策 | 选择 |
| --- | --- |
| 预览存放 | 处理结果**同时写一份临时文件到应用缓存目录**，保证每张都能当场查看 |
| 列表形态 | 保持**紧凑列表**，不改成大卡片 |
| 查看入口 | 每行**右侧加「查看」按钮**，与已保存状态一致；左侧缩略图换成结果图 |
| 批量上限 | 从 50 张降到 **20 张**（见 3.0：省的是磁盘，不是堆） |

## 3. 实施内容

### 3.0 批量上限从 50 张降到 20 张

**注意：这一条不解决堆内存问题，它解决的是缓存目录占用。** 已确认结论如下（2026-09-16 真机核查）：

- 处理是逐张串行的，每张结束立即 `recycle()`，所以**堆峰值由单张图尺寸决定，与批里张数无关**。50 张改 20 张对堆峰值几乎没有影响。
- 唯一随张数增长的是结果缓存（`ResultCache`），而它已有硬预算 `min(32MB, maxMemory/8)`，超限淘汰最旧项——20 张和 50 张的堆占用上限相同。
- 真机证据：dropbox 崩溃记录中本应用 0 条；Java 堆占用 28.5 MB，Dalvik 峰值 19 MB；堆上限 256 MB（大堆 512 MB）。**没有实际发生内存崩溃。**
- 降上限的真实收益：预览文件写在磁盘缓存目录，一批 50 张大图的预览可能占上 GB，降到 20 张可把这块占用压到约 40%。

需要同步修改的数量相关位置：

| 位置 | 现值 | 改为 |
| --- | --- | --- |
| `BatchProcessor.add` 校验与提示 | 50 | 20 |
| `BatchJournal.read` 的 `require(length <= 50)` | 50 | 20（旧任务记录超过 20 张时按现有异常路径提示重建列表） |
| `BatchUi` 选择器 `PickMultipleVisualMedia(50)` | 50 | 20 |
| `BatchUi` 按钮「继续添加图片（N/50）」与说明文案 | 50 | 20 |
| `BatchDeviceTest` 上限用例 | 51 张 | 21 张 |

### 3.0.1 顺带加固的两个内存缺口

这两条才是真正针对堆的改动：

1. **修正内存预算公式的量级偏差**。`maxPixels` 现在按 **32 字节/像素**（即 1 倍 ARGB）计算：

   ```kotlin
   val maxPixels: Long = minOf(8_000_000L, (Runtime.getRuntime().maxMemory() * 0.60 / 32).toLong())
   ```

   但一次处理的实际峰值分配约为 **5 倍**图片大小：`load()` 期间解码位图与归一化位图**同时存在**（2×），`transform()` 再叠加像素数组（1×）、输出位图（1×）、`traversal` 路径数组（1×）。
   图片尺寸是离散的，一张刚好通过校验的图紧接着就要约 5 倍内存，再叠加 `retainedBytes` 就可能超预算。
   改为按 5 倍预留，并让上限随可用堆自适应，界面文案不再写死 800 万像素。

2. **`transform` 的预算缺口**。`retainedBytes`（单图页已打开的大图）目前只用于限制 `load()` 的解码尺寸，**没有算进变换阶段**。改为处理每张前按「可用堆 − 已保留字节」复核，不足时该项如实报错，而不是强行分配。

### 3.1 暂存文件承载处理结果

处理完每张后，把**编码结果字节**写入应用私有目录，而不是只留在内存：

```
filesDir/batch/<batchId>/<itemId>.<png|jpg>
```

选用 `filesDir` 而非 `cacheDir`：系统可能回收缓存目录，而这里的文件在用户做出"存/删"决定前都必须可靠存在。
用 `item.id` 命名，改写或换格式时覆盖，不留垃圾。

| 环节 | 行为 |
| --- | --- |
| 处理 | 解码 → 变换 → 编码 → 写暂存文件 → 标记「已处理」 |
| 查看 | 缩略图与全屏预览都读暂存文件 |
| 存相册 | 读暂存文件字节 → 写入 MediaStore → 成功后删除暂存文件（内容已移走，不留副本） |
| 删除 | 删暂存文件并移除该行；**不碰原图、不碰相册** |
| 写暂存失败 | 该项标记失败并说明原因；已处理的其他项不受影响 |

因为暂存文件就是真相来源，内存中的 `ResultCache` 可以取消，省掉那 32 MB 堆占用。

**后台行为：切后台继续跑完，用前台服务保证**（2026-09-16 用户确认）：

| 项 | 决定 |
| --- | --- |
| `MainActivity.onStop()` 里的 `batch.stop(background = true)` | **移除**。切后台与息屏都不再主动取消任务 |
| 后台能否跑完 | 由**前台服务 + 常驻通知**保证，不依赖系统对后台进程的宽容 |
| 常驻通知 | 处理／保存期间显示「番茄混淆正在处理 · 第 N / M 张」；任务结束后移除 |
| 通知权限 | 需要 `POST_NOTIFICATIONS`，Android 13+ 需运行时申请。**用户拒绝时通知不可见，但前台服务仍可运行**，处理继续进行 |
| 从最近任务划掉 App | 处理停止，不做 `stopWithTask="false"`——划掉就应该停 |

实现要点：

1. **`BatchProcessor` 从 `viewModelScope` 挪到应用级作用域**。现在它挂在 ViewModel 上，Activity 销毁即结束；改为由一个应用级单例持有，前台服务与界面**共用同一个实例**，界面重建后仍能看到进行中的任务。
2. 新增前台服务（`foregroundServiceType="dataSync"`），在处理或保存开始时启动、结束时停止，并随进度更新通知文案。
3. 已知限制：`dataSync` 在 Android 15+ 有每日累计时长上限（约 6 小时），且该类型严格来说针对数据传输。**需要在真机（Android 16）实测长时间处理是否稳定**，若被系统限制则如实记录，不宣称无限时长。

**进程被杀的语义：重启即全新状态**（2026-09-16 用户确认）：

用户明确要求进程被杀后**结果直接丢失即可**，不要断点续跑。

| 时机 | 行为 |
| --- | --- |
| Activity 因旋转／切后台重建 | 应用级单例仍存活，**任务与结果照常保留**（这不是"被杀"，属于正常重建） |
| 进程被系统杀死后重新打开 | 清空任务记录与暂存目录，列表为空，**全新状态**；不做恢复、不做核对、不做断点续跑 |

因此**取消现有的启动时恢复逻辑**（`BatchJournal` 读取 → `reconcile()` 核对相册）。任务记录仅用于**同一进程内**的保存安全（保存前先落盘 `SAVING`，避免中断后重复写文件），不再承担跨进程恢复职责。

这与「先看结果再决定存删」不冲突：暂存文件在**同一次运行期间**仍在磁盘上，进程被杀时随启动清理一并删除。

### 3.2 任务记录精简

`BatchJournal` 不再承担跨进程恢复职责（见 3.1 末段），改动如下：

- **删除启动时的恢复逻辑**：不再 `journal.read()` → `reconcile()` 核对相册，启动时直接清理任务记录与暂存目录。
- **保留同一进程内的保存安全**：保存前先把该项落盘为 `SAVING`，中断后不重复写同一文件；`findPublished()` 按精确文件名核对的能力保留（用于同一会话内的重试）。
- **数量校验 50 → 20**，并容忍旧记录缺暂存字段；旧记录一律按"全新状态"清理，不做迁移。

### 3.3 列表显示结果

| 状态 | 左侧缩略图 | 状态文字 | 右侧按钮 |
| --- | --- | --- | --- |
| 未处理 / 处理中 | 原图缩略图 | 读取中 / 处理中 | 移除 |
| **已处理** | **结果图缩略图** | 已处理 | **查看**（全屏看暂存结果）、勾选框 |
| 已保存到相册 | 结果图缩略图 | 已保存到相册 | 查看（打开相册里的文件） |
| 失败 / 待核对 | 原图缩略图 | 失败 / 待核对 | 重新选择原图 |

- 「查看」打开全屏预览，复用单图页已有的 `Dialog` + 双指缩放实现，保持交互一致。
- 缩略图本身也可点，效果等同于「查看」，避免按钮太小不好点。
- 暂存文件缺失的项显示「结果已失效，请重新处理」，不假装能看。

### 3.4 处理中就能保存

现有代码已是逐张处理，所以第 1 张处理完就立刻出现在列表里，不需要等整批。
勾选框在每张处理完成后立即可用，「保存选中的 N 张到相册」随时可点。

- 保存时 `saving = true`，此时禁用勾选与保存按钮、隐藏「停止任务」，避免并发。
- 不做计算与保存的并发，避免内存峰值叠加。
- 已保存项不再重复生成文件（现有 `findPublished` 按文件名核对，逻辑保留）。

### 3.5 清理

| 时机 | 动作 |
| --- | --- |
| 存相册成功 | 删除该项暂存文件（内容已移走） |
| 用户删除某项 | 删除该项暂存文件；不动原图与相册 |
| 清空列表 / 新建任务 | 删除整个批次暂存目录，不删除相册图片 |
| 重新选择原图 | 删除该项暂存文件（结果已失效） |
| 应用卸载 | 系统清理应用私有目录 |

### 3.6 不改的部分

- 不自动保存到相册；保存始终由用户显式触发。
- 批量仍是「每张处理 1 次」，不提供批量次数输入。
- 保存文件名规则、`Pictures/TomatoShuffle` 目录不变。
- 不做批量分享或 ZIP 打包。
- 不做跨进程恢复、断点续跑、从最近任务划掉后继续运行。

## 5. 验证

1. 单元测试（暂存）：3 张处理完成后每项都有暂存文件且可解码；保存 1 张后其余暂存仍在；`clear()` 后批次暂存目录为空。
2. 单元测试（零重算）：保存出的字节与处理阶段写入的暂存文件**逐字节相同**，证明确实没有重算。
3. 单元测试（上限）：21 张被拒绝且列表不变化，错误提示写明 20。
4. 单元测试（内存）：保留字节使预算不足时，该项标记失败并给出原因，不抛出 `OutOfMemoryError`。
5. 单元测试（全新状态）：存在旧任务记录与残留暂存文件时启动，列表为空且残留被清除。
6. 真机 instrumentation：用慢速 `transform` 桩确认第 1 张完成后其结果可读、第 2 张仍在处理；确认处理阶段相册无新增文件；确认存相册后暂存被清理。
7. 真机手工（需你确认后进行）：
   - 选 3～5 张解混淆，逐张看结果、删掉不满意的、把满意的转存相册。
   - **切后台再返回**：处理不中断、结果仍在。
   - **息屏 10 分钟再返回**：处理应已继续或完成，通知文案随进度变化。
   - **从最近任务划掉 App**：处理停止。
   - **划掉后重新打开**：列表为空、无残留暂存文件。
   - 拒绝通知权限后再处理：服务仍能运行，处理不被阻断。
8. 回归：`clearImage`、单图「指定次数」、既有单测与既有设备测试。

## 6. 风险与边界

- **前台服务的平台风险**：`dataSync` 在 Android 15+ 有每日累计时长上限（约 6 小时）；该类型严格来说针对数据传输。必须真机实测长时间处理是否被系统限制，**不宣称无限时长**。
- **通知权限被拒**：Android 13+ 用户拒绝后通知不可见，前台服务仍可运行；界面必须说明处理在后台继续，避免用户以为卡住。
- **磁盘占用**：暂存是处理结果的完整副本，20 张大图可能占数百 MB 应用私有空间。清理规则见 3.5。
  **总量上限与长期增长的防护本轮不做，已记录为下一轮事项（见第 8 节）。**
- **降上限不等于更安全**：20 张上限降低的是磁盘与列表长度，堆峰值仍由单张图尺寸决定（见 3.0）。真正的堆保护来自 3.0.1 的加固。
- **格式差异**：暂存文件就是发给相册的那份字节，因此预览与最终文件一致；JPEG 质量按批参数冻结，沿用现有版本说明，不宣称与网站逐字节一致。
- **进程被杀**：按要求不做恢复，重启即全新状态；已保存到相册的图片不受影响。
- **不做**：自动保存、批量次数、跨进程恢复、划掉后继续运行。


## 7. 执行方式（已确认）

1. 按第 3、4 节实施代码。
2. 跑单测 + 编译 + lint + 打 APK（同一调试签名，可覆盖安装）。**构建完先向用户报告结果，不自行安装、不自行跑真机测试。**
3. 由用户决定是否跑真机 instrumentation 测试与安装新包；确认后再执行。
