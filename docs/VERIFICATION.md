### 内存实测（2026-09-16，vivo V2505A / Android 16）

| 输入 | 结果 |
| --- | --- |
| 运行时堆上限 | `Runtime.maxMemory()` = 256 MiB，`memoryClass` = 256 MiB，`largeMemoryClass` = 512 MiB，非低内存设备 |
| 8.0 MP（3264×2448） | 加载与变换成功；变换期间堆占用峰值约 **91 MiB**，结束后剩余约 **162 MiB** |
| 1.9 MP（1600×1200） | 接受；混淆后解混淆**逐像素往返一致** |
| 编码期占用 | 按每像素 16 字节计约 128 MiB，仍在预算内 |
| 计算出的上限 | `maxPixels` = 8,000,000（受 800 万硬上限约束） |

该实测同时用于修正一个真实缺陷：0.2.0 开发中曾把预算改成"5 倍帧 ÷ 堆的 60%"，
导致 256 MiB 设备上限被压到约 126 万像素，连 1.9 MP 普通照片都被拒绝。
现改为按**可用余量**计算（每像素 16 字节 + 固定保留 48 MiB），并以本次实测数据为依据。

  - 通知权限被拒绝时处理仍能继续

## 算法对照方法

从[参考网站](https://xiaofanqiehunxiao.com/)的 2026-09-12 页面提取两个无副作用的曲线函数，在隔离的
Node VM 中执行；未执行广告、统计或整站脚本。记录源码摘要于 `reference-capture.json`，生成 16 种
尺寸的正向和逆向像素索引向量。

将 App 独立 Kotlin 实现与这些向量比较，全部一致。Kotlin 曲线实现改编自
[Gilbert BSD-2-Clause 项目](https://github.com/jakubcerveny/gilbert)，开源许可已写入源码目录和
App 帮助页。

本结果证明约定尺寸下的**像素置换规则一致**，不能扩大为整个网站和所有设备的完整兼容认证。
网站每次操作重新压缩 JPEG，App 在导出时才编码；没有承诺 JPEG 字节或解码后的像素无损一致。

## 图片文件往返

本地安卓测试执行：生成不透明 PNG → App 导入／规范化 → 混淆 → PNG 编码写入文件 → App 重新导入
→ 解混淆 → 与首次导入像素逐个比较，结果一致。

## 内测限制

- 未保存的图片只保留在进程内；进程被系统回收后需重新选择，应用内暂存结果会一并清理。
- 透明背景合成黑色，统一为 sRGB；PNG 无损仅指当前规范化像素。
- 超过本机像素／文件体积上限会拒绝，不静默改变待解混淆图片的尺寸。
- 当前 APK 保留调试及诊断依赖，体积尚未做正式发行优化。
- 正式发布签名、应用市场要求及全机型验收尚未完成。
