## 1. 本轮目标

保留已经可用的单图操作，新增两个相互独立的功能：

| 模式 | 输入 | 一次执行的行为 | 例子 |
| --- | --- | --- | --- |
| 原有单图模式 | 一张图片 | 混淆一次，或解混淆一次 | 与现有使用方式一致 |
| 新增批量模式 | 多张图片 | 每张都混淆一次，或每张都解混淆一次 | 选择 20 张图，分别解混淆一次 |
| 新增单图多次操作 | 仅一张图片 | 对当前画面混淆 N 次，或解混淆 N 次 | 对一张图解混淆 5 次 |

**本轮批量模式不设置次数，也不允许为多张图分别指定次数。**一批图片有不同的历史混淆次数时，可先统一处理一次，再转到单图页面继续处理。

全部操作继续在本机完成，不引入账号、广告或图片上传。

## 2. 批量混淆／解混淆

### 2.1 页面与使用流程

主页增加“单张处理 / 批量处理”切换入口，默认进入单张处理。

批量操作流程：

1. 点击“选择多张图片”，通过系统选择器添加 JPEG / PNG。
2. 展示缩略图、文件名、已选数量，支持继续添加、移除单张和清空列表。
3. 同一 URI 重复添加时去重；不承诺识别内容相同但来源不同的文件。
4. 选择“批量混淆”或“批量解混淆”，界面固定显示“每张处理 1 次”。
5. 查看输出格式和保存位置，点击明确标注的“开始混淆并保存”或“开始解混淆并保存”。
6. 逐张处理、逐张保存，完成后显示成功、失败、取消／未处理数量。
7. 从结果列表查看成功图片，或仅重试失败项。

建议首版一批最多 **50 张**；这是待审核的产品上限，最终结合目标手机实测调整。系统选择器允许数量较少时尊重其限制，应用自身也校验上限。

### 2.2 保存规则

- 批量开始按钮同时表达保存意图，避免完成后再要求逐张点击保存。
- 默认 PNG，允许整批统一使用 JPEG；任务开始后冻结本批参数。
- 沿用当前相册目录 `Pictures/TomatoShuffle`，每个输出都是新文件。
- 原图不覆盖、不删除；列表移除仅移出待处理队列。
- 处理完一张便释放不再使用的大图缓冲，只保留小缩略图、URI 和任务状态。
- “成功”必须表示结果已保存完成，不能仅表示算法计算结束。
- 同一任务项使用稳定标识关联输出，重试时跳过已成功项，防止重复保存。

### 2.3 进度与异常

| 情况 | 计划行为 |
| --- | --- |
| 正常处理 | 显示“第 3 / 20 张”、当前文件及读取／处理／保存阶段 |
| 整体进度 | 按已完成项统计；当前图片另显示真实处理进度，不伪造剩余时间 |
| 单图格式、尺寸或文件读取失败 | 标记该项失败并说明原因，继续处理其他图片 |
| 存储空间不足或出现持续资源问题 | 暂停整批，保留已保存结果，提示释放空间后重试 |
| 用户停止 | 取消可中断的读取／计算；如果正在提交保存，完成当前保存或清理未完成文件后停止 |
| 部分成功后停止 | 保留成功图片，尚未执行的项目显示“未处理”，不混入失败数量 |
| 重试失败项 | 从原始输入重新执行一次，沿用该批参数，不对失败时的中间结果再次混淆 |
| 原图访问权限已失效 | 提示重新选择相关图片，不申请整个相册权限兜底 |

“停止任务”会结束本次执行；再次处理未完成项需要用户主动点击。首版不额外增加运行中的手动“暂停／继续”按钮，避免状态过多。

### 2.4 切后台与重启

本轮建议以**前台批量处理**为范围，不承诺锁屏后或进程被杀死后仍能持续运行。

- 屏幕旋转保留队列和状态。
- 切到后台时请求在安全边界暂停；返回后由用户继续，不依赖后台持续执行。
- 保存最小任务清单（任务标识、输入引用、输出引用、参数、状态），不额外建立原图历史图库。
- 进程重启后核对已保存项，将未完成项标为中断，不自动重复执行；权限无法恢复时要求重新选择。
- 保存结果与清单更新之间发生中断时，通过任务项标识核对输出；状态仍无法确定的项显示“待核对”，不直接重试制造重复文件。
- 完成／放弃任务后可清除任务清单；清除清单不删除已经导出的相册图片。

后台通知、长时间锁屏执行与自动断点续跑建议放到后续版本，届时再核验目标系统限制、权限和执行方案。

## 3. 单张图片的多次混淆／解混淆

### 3.1 操作方式

保留现有“混淆”和“解混淆”按钮，一次点击仍执行一次。在单图工作台增加“指定次数…”入口。

点击后弹出操作面板：

- 方向：混淆 / 解混淆。
- 次数：数字输入与加减按钮，建议范围 **1～100 次**。
- 快捷值：3 次、5 次、10 次。
- 每次打开默认 1 次，避免沿用上次的大次数造成误操作。
- 执行按钮直接写明“混淆 5 次”或“解混淆 5 次”。

执行对象是**单图页面当前显示的图片**。例如已经混淆 2 次，再执行“混淆 3 次”，等价于从本次导入状态累计混淆 5 次。每次批量操作仍固定为一次，不出现此面板。

### 3.2 结果与取消

- 成功后一次性更新预览，用户继续自行选择保存或分享。
- 只导出最终结果，不生成 N 份中间图片。
- 执行失败或取消时，保留操作前的画面与计数，不提交半完成结果。
- 当前会话计数按 N 累加；混淆与解混淆分别统计。
- “重置”继续回到本次导入状态，清空本次会话操作计数。
- 对外部导入的图片，明确历史次数未知；不自动猜测解混淆次数，也不宣称已经还原成功。
- 次数表示像素变换次数，不作为“加密强度”或安全等级。

### 3.3 性能与画质

根据当前算法代码，连续执行 N 次同方向变换，可以合并为沿同一曲线的一次等效位移。计划在通过对照测试后采用该优化，避免将处理时间和内存分配次数直接放大 N 倍。

- 不反复保存、读取 JPEG，中间过程始终使用像素数据。
- PNG 保存最终像素，JPEG 仅在最终导出时编码一次。
- 优化结果应与“在本 App 内连续手动点击 N 次”逐像素一致。
- 不承诺与网站每轮 JPEG 重压缩后的像素完全一致；该差异沿用现有版本说明。
- 界面显示实际计算进度，不显示并未真正执行的“正在逐轮处理第几次”。

文件名示例（如果本轮批准加入）：

`Tomato_mix3_20260916_153000_A1B2.png`

其中 `mix3` / `restore5` 只表示这次执行的方向和次数，不代表图片完整历史。加入时间与唯一标识防止重名；不以文件名作为可靠的自动解混淆依据。

## 5. 技术拆分（供实施时参考）

### A. 核心算法

扩展 `GilbertShuffle.transform` 接收次数，默认值为 1，保持现有调用兼容。

设像素数量为 M，现有单次偏移为 `s = round(((sqrt(5)-1)/2) × M)`。N 次的合并偏移为 `(s × N) mod M`，正反向映射分别处理。计算使用 Long 中间值。

应先计算单次偏移再乘次数，不能改成对 `((sqrt(5)-1)/2) × M × N` 重新取整，否则部分尺寸会与连续单次操作不一致。保留原有负数向下取整规则。

### B. 单图状态

沿用现有 `EditorViewModel` 和图片导出链路。多次处理整体提交一次，只有成功后更新图像和次数，保留现有取消与异常行为。

### C. 批量队列

独立维护队列状态：待处理、读取中、处理中、保存中、成功、失败、取消、暂停／中断、待核对。

逐张解码和处理，避免一次加载全部全尺寸位图。同一时间只执行一个图像处理任务；内存预算包含仍保留的单图会话和缩略图。批量预览不长期持有每张完整原图和结果图。

复用 `ImageRepository`，补充稳定输出标识、结果清单及保存失败清理。队列持久化方式在实施时按数据量选择轻量结构，不为本地工具引入服务端。

### D. 升级与交付

计划版本为 `0.2.0`，显示名称统一为“l君の番茄混淆”，递增 versionCode。保留包名；构建前核对 v0.1 的签名证书并沿用同一密钥，以支持覆盖安装和保留设置。若密钥不匹配，不能默认要求用户卸载来规避，需要先说明原因和迁移影响。

## 6. 验收标准

| 范围 | 验收内容 |
| --- | --- |
| 单次兼容 | N=1 与旧版和已有网站向量一致；旧版基本流程不退化 |
| 多次正确性 | N=1、2、3、5、10、100 与独立重复调用单次算法的结果逐像素一致 |
| 多次可逆 | 同一规范化像素输入，混淆 N 次后解混淆 N 次完全恢复；包含奇偶尺寸、横竖图和单像素图 |
| 次数校验 | 空值、0、负数、非整数和超上限不能开始；输入错误有明确提示 |
| 提交与取消 | 取消或失败后画面和计数不变；无进度回调空值崩溃；单图仅保存最终结果 |
| 批量正确性 | 1、2、20、50 张的每项结果与单图处理一次一致；51 张被正确限制 |
| 批量健壮性 | 混入损坏、超尺寸或失去权限的图片，不影响其他可处理项；失败原因可见 |
| 保存与重试 | 成功数量对应实际已保存文件；成功项不重复保存；失败重试以原始输入为起点 |
| 中断行为 | 计算中停止、保存中停止、切后台、屏幕旋转、进程中断后状态符合本计划 |
| 内存与存储 | 真机批量大图不会同时驻留全部位图；存储不足保留已有结果并停止继续写入 |
| PNG 完整流程 | 混淆 → 保存 → 重新导入 → 对应次数解混淆，规范化像素一致 |
| 名称展示 | 桌面、主页、设置及分享说明统一显示“l君の番茄混淆”；窄屏、大字体不遮挡操作入口 |
| 升级安装 | v0.1 覆盖安装 v0.2 成功，名称更新，设置仍在，既有相册图片不变 |

测试先运行核心和本地 UI 自动化，再用用户正在正常使用的手机验证选图、相册、后台切换及真实大图。记录实际手机型号、系统版本、图片数量、耗时和峰值内存，不以桌面测试替代真机结论。

### 9.3 首次源码提交范围

| 纳入源码仓库 | 不纳入源码仓库 |
| --- | --- |
| `app/src/`、`core/src/` 及必要的模块构建文件 | `.tools/`、`.gradle/`、`.kotlin/`、各模块 `build/` |
| 根构建配置、Gradle Wrapper 脚本／JAR／校验配置 | 本机 SDK、JDK、Gradle 安装包及下载缓存 |
| 通用构建脚本、样本生成脚本 | `local.properties`、IDE 工作区设置、临时日志和崩溃转储 |
| 经过审查的 README、PLAN、历史计划和验证说明 | `.research/` 网页快照及临时抓取代码、`.learnings/` 本地排错记录 |
| 必要的第三方许可与来源说明 | 签名密钥、密钥密码文件、令牌、SSH 私钥和真实环境配置 |

实施时按审核过的路径分组暂存，不直接将整个工作区全部加入提交。不能用忽略所有 JAR 的方式误排除 `gradle-wrapper.jar`；示例配置只能包含占位值。

### 9.4 整理与检查步骤

1. **整理忽略规则。**覆盖上述缓存和产物目录，检查 `.env`、签名配置、私钥等文件类型；只排除不应提交的文件，不删除用户的本地文件或工具环境。
2. **整理名称与文档。**README 统一新名称，清晰区分已经实现的功能与 v0.2 计划；保留历史截图和验证记录的原版本标签，不将旧结果标成新版本验收。
3. **移除本机依赖。**构建入口接受 SDK／JDK 参数或通用环境配置，去除对特定个人安装目录的依赖；中文路径构建方案保留为可选兼容路径，并核验目录联接目标。
4. **扫描候选文件。**检查密钥、令牌、邮箱／用户名／绝对路径、个人照片、设备日志及超大文件。发现风险时报告位置和类型，不在日志中打印凭据内容。
5. **检查许可证与素材。**保留 Gilbert BSD-2-Clause 许可及其他必要声明；区分参考网站和本应用，避免让读者误认为官方客户端或受其授权。原创许可证待用户决定。
6. **初始化本地 Git 并分组暂存。**建立基线提交，检查 `git status`、`git ls-files`、`git diff --cached --stat` 和 `git diff --cached --check`，复查实际将上传的内容。
7. **检查已提交历史。**如果后续发现凭据曾被加入提交，仅补 `.gitignore` 不足以解决，应在推送前处理相关历史；已暴露的凭据另行失效／更换。历史改写前先明确影响。
8. **干净检出验证。**从本地 Git 仓库检出到临时目录，确认构建不依赖未跟踪的 `.tools`、研究快照或本机配置。运行算法／UI 测试、Lint 与 APK 构建，保留结果摘要。
9. **形成推送清单。**列出提交版本、包含文件、排除范围、许可证状态、验证结果，以及拟使用的远程地址和可见性，作为可审查的推送准备结果。

准备阶段完成上述本地工作后，才进行用户要求的远程操作。若接入已有非空远程仓库，先检查其分支和历史，采用兼容的分支／合并方案，不以强推或删除远程内容作为默认处理方式。

### 9.5 GitHub 自动化构建计划

推送准备阶段可以编写 CI 工作流；实际运行和仓库权限配置在远程仓库建立后进行。

- 在主分支推送和拉取请求时运行核心测试、安卓本地测试、Lint、调试 APK 构建；SDK、JDK 与 Gradle 版本和工程保持一致。
- 优先在标准 Linux 环境验证；如存在 Windows 专用测试假设，修复环境依赖并保留必要的 Windows 验证说明，不静默删除有效测试。
- 初版 CI 不默认运行真机测试；模拟器／真机验收与本地替代测试的结果分别记录。
- 工作流默认仅需要读取源码；第三方 Actions 固定到审查过的提交，不让普通 PR 检查具备发布权限或使用正式签名密钥。
- 测试报告和检查用 APK 作为临时构建产物，不回写到 Git 仓库，不自动发布 Release。
- 工作流的具体 API、Actions 版本、运行环境及账户资源配置，在实施时核实；本计划不假定 CI 已配置成功。

### 9.6 签名与安装包发布

这是保持用户手机能够正常升级的关键项：

- 先记录现有 v0.1 APK 的签名证书指纹，并确认对应密钥仍可使用；密钥单独安全备份，不纳入 Git 或源码 ZIP。
- 保留包名与同一签名，递增 versionCode，验证 v0.1 → v0.2 的覆盖安装。
- CI 自动生成的调试密钥可能不同，**CI 检查用 APK 不能直接替代现有用户的覆盖升级包**。
- 初期升级包可继续由持有原密钥的本机构建；只有明确需要 CI 签名时，才单独规划加密凭据与受控发布流程。
- 签名密钥变更、仓库公开、APK 发行是不同事项；不因准备推送源码而自动更换密钥或公开发布安装包。
- 后续如需 GitHub Release，附件使用已验证的 APK、SHA-256 和更新说明，注明内测／正式版本及安装要求；标签和说明对应实际验收的提交。
- `v0.2.0` 标签在该版本完成验收时创建，不为尚未实现的计划提前标记版本发布。

### 9.7 分阶段交付

| 阶段 | 交付物 | 是否涉及远程写入 |
| --- | --- | --- |
| G1. 本地整理 | 忽略规则、通用 README／构建脚本、候选文件审查 | 否 |
| G2. 本地仓库与验证 | 基线提交、干净检出构建结果、CI 草稿、推送清单 | 否 |
| G3. 接入 GitHub | 根据明确目标创建或连接仓库、推送指定分支、核对远程内容 | 是，后续实际推送任务执行 |
| G4. 后续发行 | 经测试的版本标签、APK、校验值及更新说明 | 是，另随发行任务执行 |

建议在 v0.2 修改代码前完成 G1／G2，先保留可回溯的现有版本基线。G1／G2 初估额外 **0.5～1.5 个工作日**，不包含账号登录等待、功能开发或手机验收；不为此重复开发已有功能。
